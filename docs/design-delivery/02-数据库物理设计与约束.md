## 1. 物理设计基本约定

### 1.1 字段类型

| 用途 | PostgreSQL 类型 | 约定 |
|---|---|---|
| 主键 | UUID | 应用或数据库生成 |
| 时间 | TIMESTAMPTZ | 统一存储绝对时间 |
| 短文本 | VARCHAR(n) | 设置合理长度 |
| 正文 | TEXT | 不使用任意过小的长度限制 |
| 结构化快照 | JSONB | 必须有结构版本 |
| 文件大小 | BIGINT | 单位：字节 |
| 版本号 | INTEGER | 从 1 开始递增 |
| 排序 | INTEGER | 非负或明确的排序值 |
| 状态 | VARCHAR + CHECK | 限制合法枚举值 |
| 布尔设置 | BOOLEAN | 明确默认值 |

**约定：** 下文标注“可空”的字段允许 NULL；未特别标注的核心字段默认 NOT NULL。引用其他表的字段须具有对应外键或明确说明为什么不建立外键。

### 1.2 命名规范

- 数据表、字段使用 snake_case。
- API 字段使用 camelCase。
- 表名使用复数形式。
- 外键统一使用 `_id`。
- 时间字段统一使用 `_at`。
- 状态码使用大写英文标识。
- 逻辑删除使用 `deleted_at`。
- 不直接使用用户文件名作为存储路径。

### 1.3 删除原则

普通业务删除优先软删除。

不允许通过普通业务接口级联删除：

- 历史版本。
- 被历史版本引用的媒体。
- 备份记录。
- 重要审计日志。

永久清理必须经过专用维护流程，并满足引用检查和保留策略。

### 2.1 admin_users

## 3. 内容主表及版本系统

### 3.1 contents

**职责：只保存内容身份、发布状态、有效权限与当前版本指针。**

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| id | UUID | PK |
| owner_id | UUID | FK → admin_users |
| type | VARCHAR(20) | MOMENT / ARTICLE / ALBUM |
| module | VARCHAR(20) | LIFE / KNOWLEDGE |
| publication_state | VARCHAR(24) | NEVER_PUBLISHED / PUBLISHED / UNPUBLISHED |
| effective_visibility | VARCHAR(10) | PUBLIC / PRIVATE |
| published_revision_id | UUID | 可空 |
| first_published_at | TIMESTAMPTZ | 可空 |
| last_published_at | TIMESTAMPTZ | 可空 |
| created_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |
| deleted_at | TIMESTAMPTZ | 可空 |

**必须满足：**

1. MOMENT 只能属于 LIFE。
2. ALBUM 只能属于 LIFE。
3. ARTICLE 可以属于 LIFE 或 KNOWLEDGE。
4. PUBLISHED 状态必须具有有效发布版本。
5. 当前发布版本必须属于该内容自身。
6. NEVER_PUBLISHED 不应保留有效发布版本。
7. UNPUBLISHED 可以保留最后一次发布版本指针，但不允许公开访问。
8. 已删除内容不能公开访问。

有效公开访问条件：

`publication_state = PUBLISHED`

并且：

`effective_visibility = PUBLIC`

并且：

`deleted_at IS NULL`

并且：

`published_revision_id IS NOT NULL`

对于跨表版本归属，建议使用组合外键及相应唯一约束保证，而不只使用应用程序判断。

### 3.2 content_drafts

**职责：保存当前工作草稿。**

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| content_id | UUID | PK，FK → contents |
| draft_payload | JSONB | NOT NULL |
| payload_schema_version | INTEGER | 默认 1 |
| revision_number | INTEGER | 正整数 |
| based_on_revision_id | UUID | 可空，须属于同一内容 |
| last_saved_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |

一篇内容最多只有一份当前工作草稿。

`draft_payload` 根据类型保存：

**MOMENT：**

- 文字内容。
- 图片及顺序。
- 分类和标签。
- 期望可见范围。

**ARTICLE：**

- 标题。
- 摘要。
- Markdown 正文。
- 封面。
- 分类和标签。
- 期望可见范围。
- 期望 URL slug。

**ALBUM：**

- 相册名称。
- 简介。
- 封面。
- 照片有序清单。
- 每张照片的说明。
- 分类和标签。
- 期望可见范围。

业务层须按内容类型严格验证 JSONB 结构。数据库至少约束其为对象以及 Schema 版本合法。

### 3.3 content_revisions

**职责：存储不可变历史快照。**

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| id | UUID | PK |
| content_id | UUID | FK → contents |
| version_number | INTEGER | 内容内唯一 |
| published_edition_number | INTEGER | 可空，仅发布版本使用 |
| revision_kind | VARCHAR(24) | PUBLISHED / MANUAL_SNAPSHOT |
| snapshot | JSONB | NOT NULL |
| snapshot_schema_version | INTEGER | NOT NULL |
| restored_from_revision_id | UUID | 可空 |
| created_at | TIMESTAMPTZ | NOT NULL |

**唯一约束：**

- `(content_id, version_number)`。
- 同一内容内非空的 `published_edition_number` 唯一。
- `(content_id, id)` 可作为当前发布版本归属检查的组合引用目标。

说明：

`version_number` 表示历史快照序号，手动快照也会递增。

`published_edition_number` 仅在正式发布时递增，用于界面显示“第几次正式发布”。

草稿的 `revision_number` 完全独立，不与上述两个编号混用。

**不可变规则：**

- 普通业务不允许 UPDATE 已创建的快照。
- 普通业务不允许 DELETE 历史快照。
- 恢复历史时修改工作草稿，不修改旧快照。
- 只有经过授权、审计的永久清理流程可以处理归档清除。

快照内容必须包含发布当时完整的标题、摘要、正文、封面、分类、标签、URL、相册排序和媒体引用信息。

### 3.4 content_publications

**新增的当前发布投影表。**

用于公开列表、文章详情和管理界面的高频查询。

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| content_id | UUID | PK，FK → contents |
| revision_id | UUID | FK → content_revisions |
| title | VARCHAR(240) | 当前发布标题 |
| summary | TEXT | 可空 |
| category_id | UUID | 可空 |
| cover_media_id | UUID | 可空 |
| published_at | TIMESTAMPTZ | 最近发布时间 |
| updated_at | TIMESTAMPTZ | 投影更新时间 |

要求：

- `revision_id` 与 `contents.published_revision_id` 一致。
- 分类、封面和标签信息来自当前发布快照。
- 草稿保存不能更新该表。
- 更新发布时在同一个数据库事务中更新该表。
- 撤回时可以保留投影，但所有公开查询必须检查 `contents` 有效状态。

## 4. 分类与标签

### 4.1 categories

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| id | UUID | PK |
| module | VARCHAR(20) | LIFE / KNOWLEDGE |
| parent_id | UUID | 可空 |
| name | VARCHAR(100) | NOT NULL |
| slug | VARCHAR(120) | NOT NULL |
| sort_order | INTEGER | 默认 0 |
| is_system | BOOLEAN | 默认 false |
| deleted_at | TIMESTAMPTZ | 可空 |
| created_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |

规则：

- 分类最多两级。
- 子分类必须与父分类属于相同模块。
- 父分类本身不能再具有父分类。
- 不允许循环引用。
- 同一模块、同一父级下，分类名称和 slug 不得冲突。
- 删除前检查子分类及内容引用。

分类深度和跨行关系需要组合外键、触发器或事务内的业务校验，不能仅靠普通单行 CHECK 完成。

### 4.2 tags

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| id | UUID | PK |
| name | VARCHAR(100) | NOT NULL |
| normalized_name | VARCHAR(100) | UNIQUE |
| slug | VARCHAR(120) | UNIQUE |
| created_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |
| deleted_at | TIMESTAMPTZ | 可空 |

`normalized_name` 用于处理大小写、空白和必要的标准化规则。

标签重命名属于全站分类管理动作，应记录审计日志。

历史快照保留当时的标签名称及标识，避免全局重命名破坏历史版本的可追溯性。

### 4.3 content_tags

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| content_id | UUID | FK → contents |
| tag_id | UUID | FK → tags |

组合主键：

`(content_id, tag_id)`

该表仅保存当前发布投影的标签引用。

草稿标签保存在工作草稿中，不能提前更改已发布内容的标签索引。

正式发布时由不可变快照生成，并与发布指针同步更新。

### 5.6 相册排序规则

相册不需要独立的主相册表。

相册为 `contents.type = ALBUM` 的内容，其有序照片清单存在草稿和版本快照中。

首次加入照片时：

1. 有可信拍摄时间的照片按拍摄时间升序排列。
2. 没有可信拍摄时间的照片使用稳定上传顺序。
3. 相同时间使用稳定的次级排序键。

管理员手动调整并保存后，`sort_order` 成为正式顺序依据。

后续新增照片默认追加到已有自定义顺序末尾。

## 6. URL 路由与历史地址

### 6.1 content_routes

为保证当前 URL 和旧地址在同一命名空间内不冲突，建议用这一张表统一管理路径。

| 字段 | 类型 | 约束或含义 |
|---|---|---|
| id | UUID | PK |
| path | TEXT | 全局唯一，标准化完整路径 |
| content_id | UUID | 可空，指向目标内容 |
| route_kind | VARCHAR(20) | CANONICAL / ALIAS / TOMBSTONE |
| created_at | TIMESTAMPTZ | NOT NULL |
| updated_at | TIMESTAMPTZ | NOT NULL |

规则：

- `path` 全局唯一。
- 每篇当前内容最多有一个 CANONICAL 路径。
- ALIAS 指向同一内容的当前规范地址。
- 旧地址直接解析到目标内容的当前规范地址，避免多级重定向循环。
- 任何路由最终都必须经过内容发布状态和权限验证。
- 私密、撤回、删除内容不得因为历史路由存在而被访问。
- 永久删除后可以保留无内容关联的路径占用记录，避免旧地址被重新分配给无关内容。

**与早期设计的区别：**

原先使用 `slug_aliases` 单独管理旧路径。

本轮建议将其职责合并到 `content_routes`，从数据库层面统一防止当前路径和历史路径重复。

这是表结构调整，不改变「修改 slug 后保留旧地址重定向」的产品要求。

## 11. 关键事务规范

### 11.1 保存草稿

一个数据库事务完成：

1. 验证当前草稿版本。
2. 校验草稿字段和关联资源。
3. 更新工作草稿。
4. 同步草稿媒体引用。
5. 原子递增草稿版本号。
6. 提交成功后返回新 ETag。

不能先无锁读取旧版本，再执行无条件更新。

### 11.2 正式发布

发布前准备：

- 校验身份、草稿版本和线上版本。
- 验证内容和 URL。
- 验证图片已经准备完毕。

事务内：

1. 创建不可变历史快照。
2. 创建对应历史媒体引用。
3. 更新 `contents` 发布状态和当前版本指针。
4. 更新 `content_publications`。
5. 更新当前标签、媒体和搜索投影。
6. 更新规范 URL 与历史路径。
7. 更新工作草稿基线，使已发布内容与当前编辑状态一致。
8. 记录审计事件和必要的 Outbox 事件。
9. 提交事务。

任何关键数据库步骤失败必须整体回滚。

提交后再执行不能纳入数据库事务的缓存处理。

### 11.3 撤回或转私密

事务内优先更新真实有效访问状态，并记录审计及必要的投影变更。

新的匿名读取请求必须根据最新状态拒绝访问，不能等待缓存刷新任务成功。

### 11.4 恢复历史版本

1. 验证目标版本存在且属于当前内容。
2. 检查恢复所需的媒体仍然有效。
3. 检查当前草稿并发版本。
4. 将快照转换为新的工作草稿。
5. 同步草稿媒体引用。
6. 保留原历史快照和当前有效发布版本。
7. 记录恢复操作。

### 11.5 回收站恢复

恢复后：

- `deleted_at` 清空。
- `effective_visibility` 设置为 PRIVATE。
- 如果过去曾发布，则 `publication_state` 设置为 UNPUBLISHED。
- 从未发布过的内容保持 NEVER_PUBLISHED。
- 保留原草稿和历史版本。
- 不自动恢复匿名访问权限。

## 15. 文档权威性与实现边界

本文件整编已读取的 DB-RC1，并落实最终冻结 D-01～D-06。第 16–20 节为交付细化，覆盖原文中的“建议”“或”等未收敛表述。文中的约束表达式是设计说明，不是 DDL、Prisma Schema 或迁移文件。本次没有数据库实例。

字段未写可空均为 NOT NULL；ID 为 UUID，无默认表达式，服务端生成；created_at/updated_at 由服务端填充 UTC 时刻；其他未写默认值的字段必须显式写入。所有外键默认 ON UPDATE RESTRICT、ON DELETE RESTRICT，软删除不解除引用。维护清理通过专用、审计过的事务逐项解除引用，普通业务没有物理删除权限。

## 16. 收敛后的物理约束与字段补充

### 16.1 单管理员与鉴权

admin_users 增加 singleton_key SMALLINT NOT NULL DEFAULT 1，CHECK(singleton_key=1)，UNIQUE(singleton_key)，数据库最多一个管理员；username 标准化为小写后唯一。session_version > 0；mfa_enabled 为 true 时 totp_secret_encrypted 不得为空。admin_recovery_codes 增加 UNIQUE(admin_id,code_hash)，一次性消费采用 used_at IS NULL 条件更新。口令哈希算法、会话 adapter 表、TOTP 防重放记录/速率限制载体属于 IV-01，必须在 Auth.js 版本锁定后形成补充物理设计；不得自行增加第二套登录协议。

### 16.2 内容身份与三种版本

contents 增加 state_version INTEGER NOT NULL DEFAULT 1，CHECK > 0；每次发布、转私密、撤回、软删除、回收站恢复都加 1。它承载线上状态 ETag，与 draft.revision_number、revision.version_number、published_edition_number 分工不同，防止“指针未变但权限已变”的并发遗漏。

草稿初始 revision_number=1；payload_schema_version=1；revision.version_number 和发布编号都从 1 开始，各自单调递增；分配时锁定 contents 行，禁止 MAX+1 无锁分配。快照的 revision_kind=PUBLISHED 当且仅当 published_edition_number 非空且 > 0。version_number > 0。published_revision_id 只允许指向 revision_kind=PUBLISHED 的本内容快照（延迟约束触发器验证）。

UNIQUE(content_id,id) 建在 content_revisions 上。contents(id,published_revision_id)、drafts(content_id,based_on_revision_id)、revisions(content_id,restored_from_revision_id)、publications(content_id,revision_id)、search_documents(content_id,revision_id) 均使用对应的组合 FK。可空的版本引用仅在第二列为 NULL 时不检查；content_id 自身仍通过主 FK 保证存在。循环引用使用可延迟的版本 FK，事务提交时检查。

NEVER_PUBLISHED 要求 published_revision_id、first_published_at、last_published_at 全部 NULL，effective_visibility=PRIVATE；PUBLISHED 要求指针及两个发布时间非空；UNPUBLISHED 保留最后发布指针及时间，effective_visibility=PRIVATE。deleted_at 非空时不能满足公开谓词，删除事务同时设 PRIVATE；不抹除最后版本。首次发布填 first_published_at，之后不变；last_published_at 每次发布更新。

publications.revision_id 必须等于主指针，标签、媒体投影和搜索投影必须来自该快照；延迟约束触发器检查版本一致性，投影内容一致性由发布事务和重建校验保证。查询投影永远不能代替实时权限判断。

### 16.3 JSON 快照结构与分类标签引用

JSONB 结构固定为 API Payload：schemaVersion、type、module、title、summary、bodyMarkdown、desiredVisibility、desiredPath、categoryId、tagIds、coverMediaId、placements、taxonomySnapshot。draft_payload 和 snapshot 的形状相同。schemaVersion=1；数据库 CHECK JSON 为 object，完整结构由 JSON Schema 验证。taxonomySnapshot 为服务端生成，不接收客户端写入；包含 category{id,name,slug} 或 null 及 tags[{id,name,slug}]。草稿保存时刷新该展示快照，历史快照保存当时名称。

API 写入不含 taxonomySnapshot；返回时含。MOMENT、ALBUM 仅 LIFE；ARTICLE 可 LIFE/KNOWLEDGE；发布时 title 不得全空白。草稿允许空标题/正文，发布验证由内容类型实施：ARTICLE 和 MOMENT 正文至少一个非空白字符，ALBUM 至少一个 ALBUM_PHOTO。所有媒体均 READY，分类标签未删除且分类 module 匹配。

为让分类/标签删除可被数据库约束阻止，补充四张引用表（交付细化）：draft_categories(content_id UUID PK/FK→drafts, category_id UUID FK→categories)；draft_tags(content_id UUID FK→drafts,tag_id UUID FK→tags, PK二者)；revision_categories(revision_id UUID PK/FK→revisions,category_id UUID FK→categories)；revision_tags(revision_id UUID FK→revisions,tag_id UUID FK→tags,PK二者)。保存/快照事务分别同步。快照引用表只追加，普通业务不可改删。发布分类引用在 content_publications；发布标签引用在 content_tags。软删除分类/标签前锁定对应记录检查六层引用和子分类，有任一引用返回 409 RESOURCE_REFERENCED；历史引用不会因撤回消失。未引用的对象可软删除但不释放名称/slug。

categories 增加 normalized_name VARCHAR(100) NN。标准化统一 NFKC、首尾去空白、折叠连续空白、拉丁字母小写；slug 仅小写 ASCII [a-z0-9-]，长度 1–120。根节点分别 UNIQUE(module,slug) WHERE parent_id IS NULL 和 UNIQUE(module,normalized_name) WHERE parent_id IS NULL；子节点分别 UNIQUE(module,parent_id,slug) 和 UNIQUE(module,parent_id,normalized_name) WHERE parent_id IS NOT NULL。这些唯一约束覆盖已软删除数据，以避免复用歧义。UNIQUE(module,id) 支持 (module,parent_id) 组合 FK；延迟触发器阻止自指、三级分类、跨模块父子和移动后超深，并锁住相关父子记录防并发绕过。sort_order >=0。

### 16.4 媒体放置、时间与安全

media 增加 captured_at TIMESTAMPTZ NULL（可信拍摄时间）、capture_time_trusted BOOLEAN NN DEFAULT false，uploaded_at TIMESTAMPTZ NN；trusted=true 时 captured_at 非空。created_at 不是客户端 EXIF 日期。checksum_sha256 为 64 位小写 hex；size_bytes>0；width/height 同时为空或同时>0；storage_provider+storage_key 唯一。

三张媒体引用表均增加 placement_id UUID NN。草稿 UNIQUE(content_id,placement_id)，历史 UNIQUE(revision_id,placement_id)，当前 UNIQUE(content_id,placement_id)；不对 content_id+media_id 建唯一。role 为 COVER/INLINE/ALBUM_PHOTO；sort_order>=0；每个内容/快照最多一个 COVER（部分唯一索引）。ALBUM_PHOTO 的排序在所属草稿/快照/当前发布内唯一；手动重排事务采用可延迟唯一约束或整体替换，避免交换位置瞬时冲突。placementId 跨保存和历史恢复保持稳定。

coverMediaId 若非空必须有相应 COVER placement，二者 mediaId 相同。正文图片只能用受控 placement 引用，不直接保留任意对象存储 URL；渲染正文的媒体解析由 placements 对照。同一张照片可通过不同 placementId 重复使用。顺序以 placements 数组为准，关系表 sort_order 为数组下标投影；初次选择按可信 captured_at 升序，缺失时间在后按 uploaded_at/id 排；已有手动顺序新增一律追加。用户未手动重排时也保存最终数组，不在读取时动态重排。

media_variants UNIQUE(media_id,variant_type,processing_version)，processing_version>0；每种派生类型 is_active=true 最多一条；storage_key 全局唯一；width/height/size_bytes>0。公开仅 DISPLAY/THUMBNAIL 且 metadata_sanitized=true。原图一律管理员鉴权，不因任一公开内容引用而开放；派生图按请求的 contentId+placementId 校验当前快照和权限，禁止仅凭 mediaId 获得公开访问。删除媒体时锁定媒体行，保存草稿/发布也以相同锁序检查引用，引用存在即 409。

### 16.5 路由与不可公开状态

desiredPath 为完整相对路径，以 /life/ 或 /knowledge/ 开头，ASCII 小写 slug 段，无尾斜线、重复斜线、编码斜线、查询串、片段。模块对应前缀；系统 /api、/admin、/search 等路径不可占用。新路径不在草稿保存时占用，发布才原子注册；冲突 409 PATH_CONFLICT。切换旧 ALIAS 回规范路径时必须属于同一内容，否则拒绝。

content_routes：path 唯一；UNIQUE(content_id) WHERE route_kind='CANONICAL'；TOMBSTONE 要求 content_id=NULL，其他类型要求非空。规范与别名均 FK→contents，RESTRICT。公开解析先验证目标权限再返回规范地址；ALIAS 直接一次 308 至当前 canonical；不可公开和 tombstone 统一 404，不暴露标题或重定向。当前无 canonical 的已发布内容属于事务完整性错误。权限拒绝响应 no-store。

### 16.6 任务、备份与幂等

operation_jobs 增加 lease_token UUID NULL、updated_at TIMESTAMPTZ NN；attempts>=0，抢占与提交均校验租约 token，过期执行器不得覆盖新执行器结果。outbox_events 增加 lease_until TIMESTAMPTZ NULL、lease_token UUID NULL、next_attempt_at TIMESTAMPTZ NULL，用同一模式认领；至少一次投递，消费者按 event.id 去重。重试上限/退避属于 IV-06 参数，失败必须可见，不能无限静默重试。

idempotency_records 的请求摘要包含管理员、方法、规范路径、请求体和条件版本；成功响应及业务结果在同一事务提交。COMPLETED 必须有 response_status 和 response_reference，PROCESSING 不得伪装成功。同键同请求重放原状态和响应；同键异参 409 IDEMPOTENCY_MISMATCH；处理中 409 OPERATION_IN_PROGRESS。权限会话在重放前重新校验。交付默认键保留 24h（实现参数，非此前冻结值）；过期后客户端不得依赖旧键防重。

backup_runs 增加 local_status、integrity_status、offsite_status VARCHAR(20) NN DEFAULT PENDING，各枚举 PENDING/RUNNING/SUCCEEDED/FAILED，三项互不替代；原 status 表示任务生命周期。job_id 唯一。backup_copies UNIQUE(backup_run_id,copy_type,location_key)。本地文件完成≠完整性通过≠异地完成；任务可在本地成功但异地失败时显示 FAILED/降级，三个明细不得被清空。manifest 含数据库一致性点、对象清单和 SHA256、schemaVersion、恢复工具版本。checksum/size_bytes 可空仅代表未完成；SUCCEEDED 对应项必须有 checksum 和 verified_at。restore_drills.PASSED 必须有 completed_at 与 verification_summary。

audit_logs.actor_id 为管理员 UUID 的 FK RESTRICT，target_id 为历史标识不建业务目标 FK；追加写，metadata 不含正文、恢复码、密钥或原图 URL。system_settings 只接受服务端白名单 key，不允许任意写 JSON。会话、操作审计的保留期限待 IV-07 确定，不可擅自自动清除历史或媒体。

## 17. 必须执行的事务边界

固定锁序：contents → draft → 分类/标签（ID排序）→ media（ID排序）→ routes。所有发布/状态变更串行锁 contents；草稿保存也锁 contents，随后对 revision_number 条件更新。发布事务重新检查 draft ETag 与 state ETag，不能仅在事务外校验。

发布：认领幂等键 → 双版本检查 → 验证完整 Payload 与引用 → 分配两个快照编号 → 写不可变快照/历史引用 → 指针、有效权限、state_version → 发布投影/分类标签/媒体/公开搜索 → 统一路由 → 更新草稿 based_on_revision_id 并使 revision_number+1 → 审计/outbox → 保存幂等结果 → 提交。失败全部回滚，不产生“成功但仅部分发布”。

保存：校验并原子增加 draft.revision_number，同步 draft_media/categories/tags；不动线上状态、路由、投影。手动快照检查 draft ETag，不改草稿和发布指针，仅增加快照序号。

转私密与撤回：state ETag 检查；立即 PRIVATE（撤回另设 UNPUBLISHED），state_version+1，清除公开搜索；保留当前快照、草稿、路由。重新公开必须通过明确发布确认，不提供直接设置 PUBLIC 的状态接口。回收站恢复将草稿 desiredVisibility 也置 PRIVATE、revision_number+1，避免旧 PUBLIC 意图被误点发布；此项是防误公开的交付细化。历史恢复仅替换草稿并推进草稿版本，保留线上指针。

## 18. API 字段映射与索引补全

API content.id/type/module/stateVersion/publicationState/effectiveVisibility/publishedRevisionId 来自 contents；draft.revisionNumber/basedOnRevisionId/payload 对应 content_drafts；revision.versionNumber/publishedEditionNumber/payload 对应 content_revisions；PublishedContent.payload 只从主指针快照读取，列表摘要使用 content_publications。taxonomy、media、job、backup 字段 snake_case→camelCase 一一映射，不暴露 storage_key、secret、hash、任务 payload 内部参数。

所有新增引用表的 category_id/tag_id/media_id 建 B-tree 索引；revisions(content_id,version_number DESC)；publications(published_at DESC,content_id)；contents(type,module,updated_at DESC,id) 以及 deleted_at 非空部分索引；routes(content_id,route_kind)；jobs(status,next_attempt_at)；outbox(status,next_attempt_at)；audit(created_at DESC,id)。搜索 GIN/pg_trgm 和短词策略保留 IV-03，不能在没有执行计划时声称性能通过。

## 21. 交叉核对补充

三张媒体引用表 draft_media/revision_media/content_media 增加 alt_text TEXT NOT NULL DEFAULT ''，对应 Placement.altText；caption 空字符串与 NULL 均作为无说明展示，API 统一空字符串。普通 Markdown 图片使用 media://placementId 语法，解析器按所属 Payload.placements 解引用，只允许角色 INLINE。ALBUM_PHOTO 的媒体关联也独立保存 alt_text。所有角色的顺序都取 placements 数组下标，历史与投影同步保存。

operation_jobs.result 明确只由服务端写入，EXPORT 成功时形状为 {exportId:UUID,storageKey:string,checksumSha256:string,sizeBytes:integer,expiresAt:RFC3339}；resultResourceId 映射为 exportId，下载由 exportId 定位成功EXPORT任务，校验 expiresAt 后服务端流式读取。MEDIA_PROCESS 映射 mediaId；BACKUP 映射 backupRunId。result 内部存储键不出现在 API。请求创建 EXPORT 的 payload.includeMedia 为布尔，BACKUP 不接收客户端对象存储路径。

system_settings 的 siteTitle/siteIntro 对应 key=site_title/site_intro；Settings.uploadMaxBytes 和 allowedMimeTypes 来自只读实现配置，不由普通站点文案接口修改。Category/Tag/Settings GET 的 ETag 对标准化、稳定键序列化的完整资源计算 SHA256，不依赖时间戳精度。状态etag和draft.etag为响应计算字段不重复存库。

已软删除分类标签禁止新引用；因现有引用阻止删除，所以合法快照恢复不会遭遇已删分类。若迁移遗留数据破坏此不变量，历史恢复返回409并要求先修复，不静默丢弃标签。标签/分类全局改名更新当前发布投影及搜索中的名称，在事务内完成；历史 Payload.taxonomySnapshot 永久不变。PublishedContent.payload 从当前快照读取正文及分类标签ID，展示当前名称由目录资源解析；taxonomySnapshot用于历史追溯。正文/路由/媒体仍以主指针快照为准，不被全局改名重新发布。
