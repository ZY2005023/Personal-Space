# N6：最后一枚恢复码的受控换绑

2026-11-03 · 没有真实账号、数据库、迁移、部署或外部消息发送。

## 修复行为

N5中使用最后一枚恢复码登录后，因敏感动作又要求一个第二因素，无法更换已丢失的验证器。现在成功恢复登录会原子记录会话绑定的5分钟证据，进入安全页后再次输入密码，即可开始一次限定的MFA替换；确认新验证码后生成新恢复码并撤销旧会话。

只能更换验证器，不能凭该绑定令牌改密码或直接领取恢复码。新恢复码与MFA确认同一事务提交。普通TOTP登录、其他会话、旧会话、错误密码及过期证据均拒绝。查询参数recovery=1不授予权限。

开始请求丢失响应可在原期限内重放同一待绑定配置，不创建第二组密钥或延长期限。取消会立即作废待绑定配置，随后不能重启同一次恢复；界面取消前有明确提醒。确认前原验证器仍保持不变。

## 实现与契约

登录逻辑抽到admin-login.ts，Credentials提供方继续使用同一Auth.js会话。nonce在事务前由服务端生成，恢复证据、恢复码单次消费及登录审计共同提交；JWT回调保留该nonce。已核对安装的next-auth4.24.15源码会把完整authorize返回用户传给JWT回调，没有修改提供方源码。

复用SecurityChallenge模型，purpose增加RECOVERY_LOGIN且operation固定MFA_REPLACE。索引令牌与绑定令牌使用域分隔HMAC派生，数据库只存摘要；待绑定密钥仍以独立AES密钥加密。密码校验及独立持续限流保留，管理员行锁串行化证据消费与绑定变更。

安全契约0.2.0新增recovery-mfa-start，当前8操作/80引用；业务契约1.0.2及原冻结稿不变，模型仍30，没有迁移。
